# AGY 499 排查与流式修复（2026-09-28）

本次通过 SSH 只读检查生产容器、日志、部署源码和 PostgreSQL 元数据；数据库查询设置
`default_transaction_read_only=on` 和 15 秒语句超时。没有修改服务器代码、配置或服务状态，
没有读取用户提示词。下列时间均为北京时间（UTC+8）。

## 结论与边界

已确认的直接原因是：Gateway 的入站请求上下文被取消，随后取消向 Bridge 和生成进程传播。
用量记录的错误码为 `client_disconnected`，Gateway 将其保存为 `cancelled / 499`。
这不是 Google 返回了 HTTP 499，也不证明用户按了取消键。

网页监控通过独立请求读取数据库。AGY 的请求连接断开后，网页仍可正常显示网关保存的
499，因此“在网页看到 499”不能排除 AGY 到 Cloudflare、Tunnel、Caddy、Gateway
之间的通信问题。服务端现有日志不能区分这条链路上究竟哪一跳最先取消。

最明显的诱因是长时间没有首包：排查时线上 Bridge 等 CLI 完整退出及结果校验通过后才写响应；
Gateway 又完整读取并校验 Gemini 响应后才向客户端发送。在这些等待阶段，没有响应头、
模型事件或保活数据。慢生成会让整条外部链路长时间空闲，增加代理超时或连接中断的风险。
不能仅凭这些记录判定 Google 生成慢的具体原因，或断言发生了 Cloudflare 524。

## 本机协议对照

使用本机官方 AGY `1.2.12`，临时 HOME、合成 Gemini Key、严格工具权限和
`127.0.0.1` 模拟服务运行 `gemini-3.8-flash --effort high`。不访问生产推理接口，
不使用真实 Google 凭据。用户实际客户端版本和本机代理设置尚未确认。

| 模拟行为 | 结果 |
| --- | --- |
| 主请求 135 秒不发送响应头或响应体，然后返回合法 Gemini SSE | 成功返回 `OK`，无重试 |
| 立即发送标准 SSE 注释 `: keepalive` | 立即报 `invalid stream chunk: : keepalive` |
| 每 10 秒发送空 `candidates[].content.parts` 的 Gemini JSON 事件，20 秒后返回结果 | 成功返回 `OK` |

因此，AGY 1.2.12 在该隔离配置下没有固定 60/120 秒无首包取消限制；外部链路应优先
排查。标准 SSE 注释心跳与这个客户端不兼容。空 Gemini JSON 保活仅通过本地协议
验证，尚未证明能修复线上故障，也未验证所有错误、工具续轮及账务场景。

## 相关实现及改进方向

- `internal/server/api.go`：`client_disconnected` 或入站上下文取消被记录为 499。
- `internal/antigravity/server.go`：等待 `runner.Run` 完成才写 Gemini 响应。
- `internal/proxy/gemini.go`：`http.Do`、`io.ReadAll`、完整结果校验全部完成后才写首包。
- `internal/server/middleware.go`：未写响应状态时，访问日志默认记 200。因此本次相同
  请求在访问日志显示 200、在数据库显示 499；不能用访问日志的这个 200 推断生成成功。

上述 `api.go`、`runner.go` 和 `proxy/gemini.go` 在服务器检出目录与本地的 SHA-256
一致。没有替换或修改运行中的二进制。

短期可尝试 `agy --model gemini-3.8-flash --effort medium`，减少长生成进入超时窗口
的机会；这会改变思考档位，并非根治或成功保证。进一步定位最初断开的节点，需要同次
请求的客户端诊断、代理日志或 Cloudflare 边缘记录。

代码层面值得改进的是长任务的对外保活及取消诊断。实现时应在通过鉴权和准入后发送
客户端能够接受的保活事件，保留对真实模型结果的完整校验，处理“响应头已发送后上游
失败”的 Gemini 流内错误，区分首保活与首 Token，并验证取消、租约及计费。只给 Bridge
增加心跳无效，因为 Gateway 仍会 `io.ReadAll` 缓冲；只加 `: keepalive` 则会使已测
AGY 客户端立即失败。上述为初始排查结论；用户随后明确要求实现增量输出，本机改动见下节。

## 本机流式修复

用户进一步说明，创建复杂 HTML/SVG 动画时连续失败，而分析代码和创建简单文件可以
成功。这更符合长生成在缓冲链路中持续无首包的解释，不能据此认定存在写文件权限故障。
没有保存失败请求的模型输出，具体生成耗时仍不能从现有日志还原。

按后续要求，在本机实现原生 Gemini 流式输出，未修改或部署服务器：

- Runner 验证每条 CLI 事件并立即提交普通文本增量；Gateway 逐事件验证后立即刷新。
- CLI 验证初始化后发送空 Gemini candidate，之后每 10 秒保活。它没有模型输出或用量，
  不计首 Token。可能是工具调用的 JSON 保持缓冲，完整且校验通过后才执行。
- 终止结果与已输出前缀一致，完整结果、进程退出、凭据写回和流尾通过校验后才释放
  工具及最终用量。已输出后不会切换账号混合结果。
- 真实 AGY 会忽略单纯的 JSON 错误事件；已开始的失败流改为脱敏命名 SSE 错误，并在
  Gateway 完成失败记录和配额结算后中止 HTTP，防止错误流以成功 EOF 结束。
- 内部版本协商支持旧端回退。JSON 和 Antigravity Responses 的完整结果路径保持原行为，
  不新增数据库迁移或配置；生产启用需要更新 Gateway 和 Bridge 两个镜像。

真实 AGY `1.2.12` 已通过执行器完成前收到增量、最终正文不重复和错误流明确失败的测试；
真实 `1.2.4` 的合成协议测试确认其 `text_delta` 与最终文本一致。一次性 PostgreSQL
验证了工具续轮、一次结算、取消清理，以及异常 HTTP 中止前的失败/零金额结算/租约释放。
全部测试使用合成凭据和本机服务，没有调用真实 Google 推理。

Cloudflare 官方当前文档将普通代理的默认 Proxy Read Timeout 列为 125 秒，并提示
Tunnel 使用单独的 origin 参数。第一条请求约 120 秒的耗时不能单独证明是 524；其余
71～110 秒的取消也不能统一用一个 125 秒截止时间解释。

[Cloudflare 连接限制](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)。
